# Формат хранения базы CHNOSPHal (черновик v3, прототип)

Статус: **прототип, продакшн не меняется**. Базовая CHNOSP-БД
(`chposp_1000_zstd9_v2.fdb`) остаётся эталонным backend.

Документ отвечает на требования ревью: описать, что хранится и что
восстанавливается, как именно восстанавливается H, что такое «ранг/дельта»,
какие нужны внешние таблицы, какие накладные расходы у индекса, а также
протокол воспроизведения замеров.

---

## 1. Что хранится и что вычисляется

| Сущность | Хранится? |
|---|---|
| Состав без водорода (C, N, O, S, P, галогены) | **да** |
| Водород H | **нет**, восстанавливается по номеру бина и составу без H |
| Моноизотопная масса | **нет**, считается из состава в целой шкале 1e-11 Да |
| m/z | **нет**, считается из нейтральной массы и аддукта ([M-H]- по умолчанию) |
| Строка формулы | **нет**, собирается при выдаче результата |
| Порядок/принадлежность бину | **да**, неявно через смещения блоков в индексе |

Следствие: «добавить массу в запись» не требуется, потери точности нет —
расчёт детерминирован в целых числах (масштаб `MASS_SCALE = 1e11`).

## 2. Раскладка записи (вариант без H)

```
биты  поле             ширина   диапазон
0..7  C                8        0..255
8..14 N                7        0..127
15..21 O               7        0..127
22..27 S               6        0..63
28..34 P               7        0..127
35..41 X_code          7        0..125 (0 = без галогенов)
                                индекс мультимножества в таблице подстановок
```

Итого 42 бита → упаковывается в 6 байт (48 бит). Счётчик галогенов `x`
**не хранится**: он однозначно выводится из `X_code`.

Вариант «с H» (нужен только как контрольный) хранит ещё 8 бит водорода и
занимает 8 байт (`code64`), при этом в него пишется **конечный** H
(`H_final = H_framework − x`).

Используются элементы: C, H, N, O, S, P, F, Cl, Br, I (10 элементов).

## 3. Восстановление водорода (ключевое условие однозначности)

Бин `b` покрывает полуоткрытый интервал `[L, U)`, где `L = b·0.1 Да`,
`U = L + 0.1 Да` (в целой шкале `L = b·1e10`, `U = L + 1e10`).

Пусть `base` — масса состава без водорода:

```
base = C·m_C + N·m_N + O·m_O + S·m_S + P·m_P + Σ_галогены n_x·m_x
```

(в целых единицах 1e-11 Да; для `X_code = 0` галогенная часть отсутствует).

Тогда

```
H = ceil((L − base) / m_H)
```

и запись принимается, только если

```
H >= 0   и   L <= base + H·m_H < U   и   x <= H
```

**Условие однозначности:** ширина бина `w = 0.1 Да` строго меньше шага массы
при изменении H на единицу (`m_H = 1.00782503223 Да`), поэтому в интервале
шириной `w` при фиксированном `base` лежит не более одного целого `H`.
Условие не зависит от чётности DBE и от химических правил — только от шкалы
масс и ширины бина.

Проверено эмпирически (полный проход, не выборка):

| Объём | Ошибок восстановления |
|---|---|
| 4 279 646 записей (окно 300–320 Да, кап 5) | 0 |
| 3 056 записей (бин 300.05 Да) | round-trip OK |
| 228 193 записи (бин 700.05 Да) | round-trip OK |
| 2 482 549 записей (бин 999.60 Да) | round-trip OK, 5 форматов |
| 2 450 230 записей (бин 997.60 Да) | round-trip OK, 5 форматов |
| 406 008 формул (≤ 300 Да, кап 2, независимый эталон) | 0 ошибок восстановления H |

Для `m/z`-индексации условие требует `w < m_H/|z|` (при `z = ±1` и `z = ±2`
выполняется с запасом); разные аддукты/заряды должны лежать в отдельных
секциях, иначе однозначность теряется.

## 4. Что такое «ранги + дельта»

В замерах вариант «ранги+дельта» — это **не** номер строки и не требует
внешней таблицы соответствия. Это:

1. внутри бина коды без H сортируются по возрастанию;
2. в поток пишутся первый код (абсолютно) и разности между соседними кодами;
3. при чтении коды восстанавливаются префиксной суммой;
4. состав восстанавливается из кода по раскладке из §2.

Дельта-кодирование **сбрасывается на каждом бине** (каждый бин — отдельный
кадр zstd), поэтому «разрывов» между блокинами нет.

Накладные расходы: заголовков внутри кадра не требуется, кроме первого
значения; число записей берётся из индекса (§5).

## 5. Блоки, индекс и накладные расходы

Файл состоит из последовательных кадров zstd по одному на непустой бин
0.1 Да. Индекс — отдельный массив записей фиксированной длины:

```
bin_id (u32) | file_offset (u64) | compressed_size (u32) | raw_size (u32) | record_count (u32)
```

= 24 байта на блок. Измерено на продакшн-базе (7 734 блока): манифест JSON с
SHA-256 — **2.52 МБ (326 байт/блок)**; «тонкий» бинарный индекс — **0.19 МБ
(24 байта/блок)**. Для 8 231 блока новой базы это 0.20 МБ (тонкий индекс) или
≈2.7 МБ (JSON с контрольными суммами). Эти величины в оценку размера §8 пока
**не включены**.

## 6. Round-trip

Требование: `decode(encode(F), bin(F)) == F` для каждой формулы.

Проверка выполняется в `tools/bin_full_benchmark.py`: для всех записей бина
строится эталонная строка формулы, затем коды упаковываются в каждый из 5
форматов, сжимаются, декодируются и снова превращаются в строки; сравниваются
множества строк.

Результат: **все 5 форматов OK** на всех замеренных бинах, включая самые
тяжёлые (300.05, 500.05, 700.05, 997.60, 999.60 Да — до 2.48 млн записей), а
также на независимом множестве из 406 008 формул (≤ 300 Да, кап 2), где
проверено ещё и точное совпадение множеств с эталоном.

Во время отладки найдены и исправлены три ошибки:

* 6-битное поле для `X_code` (125 композиций требуют 7 бит) — приводило к
  неверному составу при декодировании;
* отсутствие проверки `x <= H` в генерации — давало записи с отрицательным
  конечным водородом;
* в независимом эталоне (собственные литералы масс) у углерода стоял лишний
  ноль (120 Да вместо 12) — эталон находил всего 242 формулы вместо 406 008.
  Ошибка найдена именно сверкой с моделью; после исправления множества
  совпали полностью.

## 7. Полнота представления «фреймворк + подстановка H→X»

Модель: конечная формула = (фреймворк CHNOSP с водородом `H + x`) минус `x`
атомов H плюс галогенный мультимножество размера `x`.

Разбор по каждому фильтру базового профиля (`_enum_valid_cnosp`,
профиль `dbe_nonnegative_even_p3_s2`):

| Фильтр | Поведение у родителя | Статус |
|---|---|---|
| `C >= 1` | C не меняется | инвариант |
| `DBE = (2C+2+N+P−H−X)/2 >= 0` | числитель `2C+2+N+P−H−X` инвариантен при H→X | **доказано** |
| целочисленность (чётность) Льюиса | тот же числитель, чётность сохраняется | **доказано** |
| `H <= 2C+2+N+P` | эквивалентно `DBE >= 0` | следствие |
| `N <= 127, O <= 63, S <= 31, P <= 63` | эти элементы не меняются | инвариант |
| `H <= 255` | родитель — сам фреймворк, его H ограничен при сборке | выполняется по построению |
| масса <= 1000 Да | масса родителя = масса конечной − Δ, Δ >= 0 | выполняется |
| `x <= H` (нужен H для подстановки) | проверяется в генераторе | проверено |
| **отношения H/C, O/C, N/C** | **H/C НЕ инвариантен** (`(H+x)/C > H/C`) | в текущем профиле таких фильтров нет; при их появлении полнота сломается — требуется явная проверка |
| прочие исключения генератора | отсутствуют | проверено чтением кода |

Эмпирическая проверка (полный перебор окна 300–320 Да, конечные формулы —
316 684): родителей вне профиля **0**, неоднозначных пар
(родитель, подстановка) **0**.

Ограничение первой проверки: она сравнивает реализацию с тем же профилем.

**Независимая проверка** (`tools/independent_crosscheck.py`): собственные
литералы масс (в шкале 1e-11 Да), полный перебор всех кортежей элементов с
отсечением по массе, заново реализованные правила (DBE ≥ 0, целочисленность
числителя, C ≥ 1) — ни один модуль `src/` не используется.

| Подпространство | Независимый перебор | Модель «профиль + подстановка» | Только в эталоне | Только в модели | Расхождений массы |
|---|---|---|---|---|---|
| ≤ 300 Да, галогенов ≤ 2 | 406 008 | 406 008 | 0 | 0 | 0 |

Round-trip на этом множестве: проверено 406 008, ошибок строк 0, массы 0,
восстановления H 0.

Остаётся не покрытым: подпространства с капом 5 и с S/P (проверка на бóльших
капах — отдельный прогон; вычислительно дороже).

## 8. Оценка размера базы

Метод: точная гистограмма заполнения бинов 0.1 Да (аналитический подсчёт по
фреймворкам) × измеренная зависимость «бит/формула от числа записей в бине»,
сложенная по всем бинам.

| Что | Значение |
|---|---|
| Записей всего (конечная масса ≤ 1000 Да, кап галогенов 5) | **2 633 587 551** |
| Записей ровно с капом 0 (текущая CHNOSP) | 79 576 593 |
| Наивно uint64 | 21.07 ГБ |
| Оценка: uint64 c H + shuffle + zstd9 (текущий формат) | **1.16 ГБ** |
| Оценка: uint48 без H + shuffle + zstd9 | **0.75 ГБ** |
| Оценка: ранги+дельта + shuffle + zstd19 | **0.35 ГБ** |
| Метаданные/индекс | +0.19 МБ (тонкий, 7 983 блока) … ≈2.6 МБ (JSON+SHA-256) |

Измеренная кривая (замеры по бинам, конечная масса в бине):

| Бин | Записей | uint64+H zstd9 | uint48 без H zstd9 | ранги+дельта zstd9 | ранги+дельта zstd19 |
|---|---|---|---|---|---|
| 300.05 | 3 056 | 8.31 | 6.00 | 5.67 | 5.30 |
| 500.05 | 39 741 | 4.59 | 3.55 | 2.68 | 2.24 |
| 700.05 | 228 193 | 3.73 | 2.38 | 1.85 | 1.31 |
| 999.60 | 2 482 549 | 3.31 | 2.12 | 1.58 | **0.83** |
| 997.60 | 2 450 230 | 3.32 | 2.13 | 1.59 | **0.84** |

Важное уточнение про ограничение диапазона: счёт «2.63 млрд» — это формулы,
у которых **конечная** масса ≤ 1000 Да. Для произвольного окна чисел меньше:
например, для 0–300 Да без ограничения конечной массы было бы 10 247 907
формул, а с ограничением — 596 620 (измерено прототипом сборки, §11).

Кривая теперь измерена **во всём рабочем диапазоне** — от 3.1 тыс. до
2.48 млн записей на бин, то есть покрывает медиану (61 679), p95 (1.58 млн) и
максимум. Оценка 0.35/0.75 ГБ получена интегрированием этой кривой по
гистограмме заполнения; экстраполяция остаётся только для бинов между
измеренными точками и ниже 3 тыс. записей.

Расхождение распределения: точный генератор даёт для бина 999.6 Да
2 482 549 записей, а гистограмма (раскладка Δ по подбинам 0.01 Да) — 2 818 123,
то есть ≈13 % для самых тяжёлых бинов. Суммарное число записей от этого почти
не меняется (2 632 818 191 против 2 633 587 551, 0.03 %), но по отдельным
тяжёлым бинам распределение приближённое.

## 9. Стоимость запроса (измерено, не оценено)

Декодирование бина, разбитое по этапам (`tools/bin_full_benchmark.py`):

| Бин | Записей | чтение | декомпрессия | обр. shuffle | распаковка+H+масса | ppm-фильтр | итого |
|---|---|---|---|---|---|---|---|
| 500.05 | 39 741 | 0.03 мс | 0.07 мс | 0.13 мс | 0.44 мс | 0.03 мс | **0.66 мс** |
| 700.05 | 228 193 | 0.04 мс | 0.67 мс | 1.12 мс | 9.61 мс | 0.59 мс | **11.99 мс** |
| 999.60 | 2 482 549 | 0.06 мс | — | — | — | — | **20.7–28.6 мс** (полный декод) |

Крупнейший бин (2.48 млн записей): полный цикл декодирования 16–29 мс в
зависимости от формата (uint48/zstd19 — 16 мс, ранги+дельта — 27–29 мс; при
этом ранги+дельта дают вдвое меньший файл). «Секунды на пик» из размера
блока не следуют — измерение это подтвердило.

Оценка «типичного» запроса зависит от
веса: равномерно по занятым бинам — 54 050 записей; по случайной записи —
1 177 354 записи. Обе величины приведены явно, вместо неопределённого
«типичный запрос».

Отдельно: полная материализация строк формул для всех записей бина стоит
~3 мкс на формулу (766 мс на 228 тыс. и 8.8 с на 2.48 млн записей) — но при
запросе строки строятся только для кандидатов, прошедших ppm-фильтр
(десятки–тысячи), поэтому это не стоимость запроса, а стоимость выгрузки
всего блока в текстовом виде.

## 11. Прототип сборки (измерено)

`tools/build_halogen_db.py` собирает диапазон в новом формате параллельно
(multiprocessing по бинам, воркер отдаёт уже сжатый кадр).

Результат прогона `--mass-min 0 --mass-max 300 --halogen-cap 5 --workers 12`:

| Показатель | Значение |
|---|---|
| Записей | **596 620** |
| Блоков (бинов) | 1 087 |
| Размер `.fdb` | **0.62 МБ** |
| Индекс `.idx` | 26.1 КБ (24 байта × 1 087) |
| бит/формула | **8.28** |
| Время | 5.2 с (115 368 записей/с на 12 процессах) |

Для сравнения: тот же диапазон без ограничения конечной массы дал бы
10 247 907 формул — ограничение «конечная масса в окне» сокращает множество
в 17 раз на низких массах (и в 3.4 раза на всём диапазоне до 1000 Да).

8.28 бит/формула для 0–300 Да выше, чем на отдельных бинах 300–1000 Да
(1.3–2.4), потому что здесь преобладают очень маленькие бины (медиана
90 записей), а малые блоки сжимаются хуже.

**Оценка времени полной сборки.** Генерация тяжёлого бина (2.48 млн записей)
занимает 71 с на ядро (35 тыс. записей/с). При 12 процессах это ≈ 420 тыс.
записей/с, то есть 2.63 млрд записей ≈ **1.7 ч** на генерацию плюс сжатие;
с учётом неравномерности и накладных расходов — реалистично **2–6 часов**.
Отдельно нужно предусмотреть память: один тяжёлый бин — до 2.5 млн Python-int
(≈200 МБ на процесс) до упаковки, поэтому воркер кодирует блок сам.
