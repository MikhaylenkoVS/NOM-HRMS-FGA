# Benchmark report — оптимизация assign_formulas (OPT-07/08/09/10)

Дата: 2026-08-17. Референтный вход: `data/test_sets/set_01/original.csv`,
окно масс 200–700 Da, `rel_error_ppm=1.0`, 305 пиков, **147 061 кандидат**.

Замеры — `python -m src.core.benchmark_assign`.

## Итог

| Метрика | До (baseline) | После | Ускорение |
|---|---|---|---|
| `_generate_candidate_formulas` (повторный вызов) | 0.094 с | **0.00046 с** | **~203×** |
| `assign_formulas` (медиана, 5 прогонов) | 0.336 с | **0.268 с** | **~1.26×** |

## Что сделано

- **OPT-10** — `@lru_cache(maxsize=16)` на генераторе кандидатов. Хэшируемый
  ключ — `(mass_min, mass_max, c_range, h_range, o_range, n_range)`. Второй и
  последующие вызовы с теми же параметрами возвращают результат за O(1)
  вместо O(N⁴). Главный источник ускорения.
- **OPT-07 / OPT-08** — предвычисление метрик всех кандидатов (`hc`, `oc`,
  `nc`, `dbe`, `ndist`, штрафы) один раз и векторизация скоринга
  (`np.where`/`np.argmin` вместо Python-цикла).
- **OPT-09** — убран `table = src.table.copy()`; результат пишется
  напрямую в `src.table` (пакетное присваивание уже было в коде).

## Честная оценка

Векторизация скоринга (OPT-07/08) на референтных данных **нейтральна по
скорости**: доминирует вычисление ppm-окна `abs_ppm` по всем 147 061
кандидатам для каждого пика (O(N) × 305 пиков), которое не зависит от ширины
окна и не затрагивается этими изменениями. Внутренний цикл уже был мал
(≈1–3 кандидата в окне 1 ppm).

Заявленное в issue ускорение ×10–30 относилось к старому коду, где в цикле
повторно парсилась строка формулы; в текущем коде (после перехода на
`cand_counts` как numpy-массив) этот бутылочный горлышек уже устранён.

Дальнейшее ускорение возможно через бинарный поиск по отсортированной
`cand_masses_ion` (O(log N) на пик вместо O(N)) — отдельная задача, не
входящая в OPT-07…10.
